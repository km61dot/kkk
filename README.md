# Smart Proxy — iOS-клиент с проверкой реальной работоспособности сервисов

SwiftUI + NetworkExtension (`NEPacketTunnelProvider`) + sing-box (`libbox`). Главная идея: сервер оценивается не по пингу,
а по тому, открываются ли через него Instagram, WhatsApp и другие сервисы; при деградации туннель сам переключает outbound.

> **Честный статус.** Код написан без Mac и **ни разу не компилировался и не запускался**. Самое хрупкое место — `Tunnel/LibboxBridge.swift`
> (привязка к API libbox, меняется между версиями sing-box). Первая сборка в CI с высокой вероятностью покажет несколько ошибок компиляции;
> они все локализуются в 1–2 файлах (см. «Если сборка упала»). Всё, что ниже названо «значением», — это стартовая гипотеза, а не измерение.

## 1. Запуск с телефона (по шагам)

1. Создай **пустой приватный** репозиторий на GitHub (ветка `main`).
2. Создай файл `.github/workflows/build.yml` (Add file → Create new file) и вставь туда содержимое файла `build.yml` из выдачи.
3. Загрузи `ProxyClient.zip` в корень репозитория (Add file → Upload files). Zip не распаковывай.
4. Actions → **build-ios** → Run workflow. Первый прогон сам распакует архив в репозиторий (и удалит zip), соберёт `Libbox.xcframework`
   из исходников sing-box, сгенерирует проект XcodeGen'ом и соберёт IPA. Libbox кэшируется, следующие сборки быстрее.
5. Артефакты: `ProxyClient-ipa` (IPA) и `diagnostics` (`build.log`, заголовки Libbox). Дальше правишь файлы прямо в веб-редакторе GitHub.

### Подпись и установка (важно)
* Туннель **не запустится** без платной Apple Developer Program: entitlement `packet-tunnel-provider` бесплатному Apple ID не выдаётся.
* Неподписанный IPA нужно подписать на компьютере/в сервисе (Sideloadly, AltStore и т.п.). Есть риск, что подписывающий инструмент не включит
  Network Extension и App Group в App ID — тогда нужен путь ниже.
* **Подпись прямо в CI** (если есть платный аккаунт): создай в developer.apple.com два App ID (`com.custom.proxyclient`, `com.custom.proxyclient.PacketTunnel`)
  с Network Extension + App Groups (`group.com.custom.proxyclient`), сертификат Apple Development и два Development-профиля с UDID своего iPhone.
  Положи в Secrets: `P12_BASE64`, `P12_PASSWORD`, `PROFILE_APP_BASE64`, `PROFILE_TUNNEL_BASE64` (base64 файлов). Тогда CI выдаст ещё и `ProxyClient-signed.ipa`.
  Как поставить такой IPA без компьютера (OTA-страница на GitHub Pages) — следующий шаг, в этот архив не входит.
* Свой префикс bundle id: поменяй `com.custom...` в `project.yml` (4 места) — App Group читается рантаймом из embedded.mobileprovision,
  так что переподпись с другим group id не ломает обмен данными.

## 4. Ядро и конфигурация

Версия: **sing-box 1.11.x** (CI берёт последний стабильный тег `v1.11.*`, можно указать свой при запуске workflow).
Libbox собирается из исходников (`cmd/internal/build_libbox`), потому что готового Apple-xcframework в релизах нет.

* **Selector `proxy`** с `interrupt_exist_connections: true` — при смене outbound ядро само рвёт соединения, привязанные к старому, и приложения
  переподключаются через новый. VPN-туннель при этом **не перезапускается**. Существующие TCP/UDP-сессии **не мигрируют** — они именно пересоздаются.
* **Свой URLTest не используем** (дублировал бы пробы и тратил батарею): решения принимает `HealthEngine` по L7-данным.
* **Clash API** (`experimental.clash_api`) на `127.0.0.1:<случайный порт>` с Bearer-секретом, генерируемым при каждом старте
  (loopback на iOS виден другим приложениям — без секрета любой мог бы переключать твой outbound). Используются эндпоинты:
  `GET /version`, `GET /connections`, `PUT /proxies/proxy`, `GET /proxies/{tag}/delay?url=&timeout=`, `DELETE /connections`.
  Нужен build-tag `with_clash_api` (CI печатает предупреждение, если не нашёл его в `build_libbox`).
* **Пробы через прокси без лишнего кода:** `/proxies/{tag}/delay` заставляет само ядро выполнить DNS + TCP + TLS + HTTP GET через **указанный** outbound —
  в том числе через не выбранный в данный момент. Поэтому кандидаты проверяются «вживую» до переключения. Системный URLSession для проб не годится:
  трафик самого расширения идёт мимо туннеля.
* DNS: DoH через selector, bootstrap напрямую; правило `outbound: any → direct-dns` резолвит адреса самих прокси-серверов без петли. `sniff` даёт домены для пассивного анализа.
* QUIC по умолчанию блокируется правилом `quic → reject` (клиент мгновенно откатывается на TCP; UDP через VLESS/VMess/Trojan нестабилен). Отключается в настройках.
* Память: `LibboxSetMemoryLimit(true)` (по исходникам libbox — GC-тюнинг и мягкий лимит Go-кучи), плюс `os_proc_available_memory()` в UI и реакция на memory pressure.

## 5. Smart Health-Check

### Пассивный уровень (что реально доступно)
iOS не отдаёт приложению TCP-метрики чужих сокетов (RTT, retransmits). Доступно только то, что видит ядро: счётчики `upload/download` каждого соединения,
домен (sniff), цепочку outbound, возраст. Из них:

| Шаг | Правило (стартовые значения, пресет «Стандарт») |
|---|---|
| Тик | каждые 2 с при трафике, 10 с в простое, 30 с после 5 мин тишины |
| «Застой» сервиса | за тик: исходящих ≥1.5 КБ, входящих <300 Б, скорость отдачи <64 КБ/с (длинная выгрузка видео — не застой) |
| Подозрение | 3 застоя подряд (≈6 с) **или** ≥2 соединения старше 8 с с 0 байт ответа и ≥300 Б запроса |
| Антишум | ≤1 подозрения на сервис в минуту; первый снимок только «прогревает» счётчики; во время наблюдения после переключения выключено |

Подозрение **само ничего не переключает** — оно только запускает активные пробы. Оно же не ловит: приложения без домена в соединении (Telegram по IP),
ошибки установления соединений (Clash API их не отдаёт), потери пакетов.

### Активный уровень
* Для каждого сервиса ≥2 независимых адреса; плановая проверка берёт **по одному** (ротация), подтверждение — **все** + 2 базовых (`gstatic`, `cloudflare`).
* Метрика одна — время до заголовков ответа (DNS+TCP+TLS+TTFB вместе). Раздельных DNS/TCP/TLS таймингов Clash API не даёт — это честное ограничение.
* **Защита от «выдуманных» адресов:** неуспех на адресе, который ни разу не отвечал ни через один сервер, считается неубедительным и в оценку не идёт.
  Исключение: если мертвы два независимых базовых адреса и ни один не жив — сервер недоступен (работает и при холодном старте).
* Частота: плановые пробы раз в 5 мин (±15 % джиттер), ×1.5 в мобильной сети, ×3 в Low Data Mode, **не выполняются, если 15 мин не было трафика**
  (после пробуждения/смены сети — одна проба через 3–4 с). Параллельно не более 2 проб.

### Модель оценки (0–100)
Для пары (сервер, сервис), вес пробы `w = 0.5^(возраст/600 с)`:
`A = Σw·ok / Σw`, `L = 1 − clamp((медиана_мс − 500)/4000)`, `score_raw = 100·(0.7·A + 0.3·L) − штраф_зависаний` (штраф 15 за событие, затухает так же, максимум 40),
доверие `conf = min(1, Σw/2)`, `score = conf·raw + (1−conf)·50` (мало данных → ближе к нейтральным 50).
Итог сервера: `0.35·средневзвешенное + 0.65·худший критичный сервис`; если базовая связность <30, итог не выше неё.
Примеры по модели (вычислены, не измерены): 5 успешных проб по 700 мс → 98; те же по 2500 мс → 85; 2 успеха и 3 таймаута подряд → ≈51 до штрафа зависаний;
сервер с Instagram 22 при остальных 95/90 → итог ≈38, а «ровный» 90/88/85 → ≈86. Веса, τ и пороги нужно калибровать на своих данных.

### Failover
1. Подозрение (пассивное или провал плановой пробы) → серия проб активного сервера (до 2 раундов, 2.5 с между ними).
2. Вердикт: `healthy` / `serviceDegraded` (≥2 провала, ≥66 % и базовая жива) / `serverDown` / `inconclusive`. Только 2 последних «плохих» ведут дальше.
3. Кандидаты: пул без активного и без находящихся в карантине (если все в карантине — берём наименее плохих). Полный раунд проб по каждому.
4. Переключение, если кандидат: базовая ≥50, проблемный сервис ≥55 и итог ≥ текущего + запас (15 в «Стандарте»).
5. `PUT /proxies/proxy` → `interrupt_exist_connections` рвёт старые соединения → кулдаун 90 с, наблюдение 120 с (проба каждые ~15 с; провал → поиск другого).
6. Старый сервер получает карантин с экспоненциальным откатом (60 с, 120 с, … до 15 мин).
7. Защита от флаппинга: кулдаун, карантин, ≤4 переключений за 30 мин (иначе заморозка на 10 мин), гистерезис возврата.
8. **Возврат на основной:** проверка раз в 5 мин, нужно 3 хороших раунда подряд (≈10+ мин), итог основного ≥ активного − 5; переключение ждёт «тихого» момента (до 90 с).
9. Смена сети (Wi-Fi↔LTE): замеры сбрасываются (они описывали другой путь), перепроверка через 4 с; пропажа сети — проверки и переключения на паузе, чтобы не «наказать» сервер за отсутствие интернета.

### Пример таймлайна (иллюстрация, не гарантия)
```
t=0.0 с   Instagram открывает ленту, соединения к *.cdninstagram.com; вверх идёт, вниз ~0
t=2/4/6 с  три тика подряд «застой» → подозрение                         (пассивное окно ≈ 6 с)
t=6–9 с   пробы: 4 адреса Instagram — таймауты/ошибки, gstatic — ок → serviceDegraded
t=9–20 с  кандидаты B и C: полный раунд (по 5–9 проб, не более 2 параллельно)
t≈20 с    B лучше на запас → PUT selector (единицы–десятки мс), старые соединения закрыты
t≈20–30 с приложения переподключаются сами (зависит от приложения)
t≈20–140 с наблюдение за B; затем штатный режим, A в карантине; каждые 5 мин проверка возврата
```
Итого ориентировочно 15–30 с от начала проблемы до восстановления; реальные цифры нужно снять на устройстве (см. раздел 7).

## 6. Ограничения iOS и как они учтены
* Лимит памяти расширения не фиксирован (зависит от устройства/iOS). В коде: Go-лимит через libbox, `os_proc_available_memory()` каждый тик (показывается в UI),
  при <8 МБ или memory pressure проверки замедляются/паузятся. Реальное значение на твоём iPhone смотри в Настройки → Диагностика.
* Фон: гарантий нет — расширение может быть заморожено/убито. Отсюда: состояние на диске, восстановление активного сервера при старте, `sleep()/wake()` с паузой/перепроверкой.
* Один цикл вместо набора таймеров; `URLSession` ephemeral без кэша; соединения анализируются не более 600 за тик; лог ядра — кольцо 200 строк; события — 120.
* MTU 1400 по умолчанию (1280/1360/1500 в настройках). IPv6 в туннеле включён, DNS-стратегия `prefer_ipv4`.
* Одно из требований ТЗ невыполнимо на iOS и заменено: «привязка соединения к приложению» (нет process-info) → привязка к **группе доменов**.

## 7. Тест-план и метрики
Инструменты: Xcode не нужен для обычных проверок — смотри вкладку «Монитор» (события, лог ядра, матрица оценок). Для замеров на Mac: Instruments (Allocations, Network, Energy),
os_signpost, Network Link Conditioner (профили 3G/«100% loss»), реальные устройства разных поколений.

| Сценарий | Как воспроизвести | Ожидание |
|---|---|---|
| Сервер жив, Instagram не открывается | заблокировать `*.cdninstagram.com` на сервере A | подозрение → serviceDegraded → переключение на B |
| WhatsApp нестабилен | подкрутить потери на сервере | падение оценки WhatsApp, переключение только при запасе ≥15 |
| DNS сломан | заблокировать DoH на сервере | провал проб, карантин; без флаппинга |
| TLS-handshake виснет | дропать пакеты после SYN на :443 | таймаут проб (6 с), `serverDown` |
| Резкое падение скорости | Link Conditioner на сервере | рост медианы, ниже L; без ложного переключения |
| Wi-Fi ↔ LTE | выключить Wi-Fi | сброс замеров, перепроверка через 4 с, туннель жив |
| Нет интернета | авиарежим | пауза проверок, без переключений и карантина |
| Падают все резервные | положить B и C | «нет кандидатов», остаёмся на A, без цикла |
| Сервер вернулся | поднять A | 3 хороших раунда → возврат в тихий момент |

Метрики качества (считать по событиям): время от начала деградации до подтверждения (TTD), до первого успешного запроса после переключения (TTR),
доля ложных переключений в час, число переключений/30 мин, расход трафика проб в сутки, средняя свободная память, % батареи в сутки с мониторингом и без.

## 8. Если сборка упала
1. Открой `diagnostics/build.log` или шаг **Build** в Actions — там список `error:`.
2. Ошибки вида «does not conform to LibboxPlatformInterfaceProtocol», «has no member …Libbox…» — правь **только** `Tunnel/LibboxBridge.swift`, сверяясь
   с `diagnostics/Libbox.objc.h` (и выводом шага «Dump Libbox headers»). Особенно: сигнатуры `updateDefaultInterface`, `findConnectionOwner`, имена `LibboxSetup`/`LibboxNewService`.
3. Если упал «Build Libbox»: проверь вывод; возможные причины — другое имя флага `-platform` в `build_libbox` для этого тега, другой Makefile-таргет.
   Можно указать тег вручную в Run workflow (`sing_box_ref`).
4. Ошибка «Clash API не поднялся» при старте — libbox собран без `with_clash_api`; добавь тег в `build_libbox` (в `_sb` перед сборкой) или пришли вывод шага.
5. Если туннель не стартует — на главном экране появится «Ошибка запуска» с текстом и логом ядра (App Group недоступна → проблема подписи/entitlements).
6. Пришли мне текст ошибок — исправлю точечно.
